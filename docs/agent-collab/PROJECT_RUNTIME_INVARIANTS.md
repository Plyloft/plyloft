# Runtime invariants for PTYs, runs, drag/drop and swarms

Read the affected sections before modifying these execution paths. These rules
retain the incident context formerly in the root AGENTS.md; other project
boundaries and verification requirements remain in that root.

- **`dragDropEnabled: false` on the main window in `tauri.conf.json`.** Tauri's default is `true`, which on macOS makes WKWebView intercept drag events at the OS layer **before** they reach the WebView's HTML5 DnD pipeline. With the default, internal JS-initiated drag-and-drop (kanban cards, files-panel-to-tile, anything similar) is silently broken — drag images follow the cursor but no `dragenter`/`dragover`/`drop` events fire on JS handlers. Cost ~6 rebuilds in v0.6.1. Trade-off: external Finder→Atelier drops bypass `WindowEvent::DragDrop` too. v0.7.3 restores that path via HTML5 drop listeners on terminal panes (`Terminal.tsx::handleHtmlDrop`) which materialize external file bytes through `fs_save_dropped_file` since the WebView File API doesn't expose `.path`.

- **The shell's drop guard owns every drop no registered zone accepts (GH #138).** With `dragDropEnabled: false` the OS hands drops to the web layer, and outside the real targets WKWebView did what a browser does: it navigated the window to the dropped file, and the whole shell went with it. `src/lib/dropGuard.ts` is installed once in `main.tsx`, on `window`, **in the capture phase**. Invariants if you touch this:
  - **Capture, not bubble.** In front of every target, so a descendant cannot get past it — the board's column delegation calls `stopPropagation()`, and a bubble-phase guard would simply never run for a drop it claims.
  - **The registry is the contract, because `defaultPrevented` cannot be.** Running first means the guard has no target claim to read. A `DropZoneRule` names a zone's root selector and the payload kinds it accepts. **A new drop target that is not in the registry will have its drops refused.**
  - **A drag is claimed by what it must be taken as.** `REQUIRED_DRAG_KINDS` (`card`, `path`, `files`) are kinds a target must accept as themselves: a Finder file arrives as `Files` *and* `text/uri-list` *and* `text/plain`, and a zone that takes one of those twins must not thereby take the file, or the file is consumed by nobody and the navigation default still stands. `uri` and `text` are alternatives — a target reading either has read the drag — so **do not** promote them to required: dragging selected text out of a web page carries `text/html` beside `text/plain`, and treating HTML as required killed those drops once already. `html` is in neither list: nothing reads it, so HTML *alone* is refused and HTML *beside* text is not.
  - **One constant per target, for both its marker and its handlers.** `TERMINAL_DROP_KINDS`, `CARD_FILES_DROP_KINDS`, `BOARD_COLUMN_DROP_KINDS`, `FILES_ROW_DROP_KINDS`, `TILE_DROP_KINDS`, `EDITOR_DROP_KINDS`. The guard refuses in capture and a target's handler runs afterwards, so a handler with a different idea of what it takes puts the copy cursor and its highlight back on a drop that was just refused — which is what `CardDetailPanel` and `Tile` did for text and URL drags before this. `dropGuard.test.ts` pins the sharing per target.
  - **Declare only what the handler reads.** `text/html` is its own kind because folding it into `text` made the terminal and tiles claim HTML-only drags they never read; the terminal declares `uri` and therefore really reads `text/uri-list`. A declaration wider than its handler is a drop that lands nowhere in silence.
  - **A text field takes text, not files.** Inserting dropped text is native and must survive, or text drag-and-drop dies across the app. Readonly and disabled fields accept nothing. CodeMirror's content takes text; **files and paths belong to the editor host around it**, which opens them.
  - **There is no "the drop failed" message, and inactivity is not evidence of a release.** Measured in Chrome with real CDP drag events: cancelling `dragover` with `dropEffect = "none"` makes the UA cancel the gesture and fire **no `drop`** (`dragenter, dragover, dragover, dragleave, dragend`); with `"copy"` the `drop` arrives. For an external drag there is no `dragend` either, so a release over a gap and the pointer leaving the window are indistinguishable in the DOM — and the signal that would separate them is the OS drag session, behind the `dragDropEnabled` flag Hard Rule #6 forbids. So the guidance is raised **while** the drag is over ground that will refuse it and taken down when the drag is claimed or ends (`guidanceFor`): one quiet toast, on screen at the release because it was on screen for the whole hover, saying where drops go rather than what just happened. `showGuidance` is asked on every event the guidance applies to and is idempotent while its handle is on screen, so the message can neither accumulate nor stay gone after its own backstop expired mid-hover — do not narrow that call back to "only when nothing is showing". `HINT_IDLE_MS` of drag silence only *hides* it. The one thing that is observed rather than inferred is a `drop` that does arrive over open ground — a release happened here and was refused — and that is announced once, as an ordinary toast that outlives the gesture. Do not reintroduce a timer and call its expiry a release.
  - **One gesture is told once, and one handler takes a drop.** Crossing a real target takes the guidance down and coming back does not put it up again; only a release, a `dragend` or `GESTURE_GAP_MS` of silence starts a new gesture, and that silence concludes nothing about how the last one ended. Where two handlers sit on one path — a tile and the terminal pane inside it — the outer one asks `nestedZoneOwnsDrop` and stands down, or the dropped path is written to the PTY twice (GH #138 F13).
  - Drags that started inside the app (`dragstart` seen in this document) are refused but never announced.
  - The board's column delegation claims **card moves only**, through `dragIsCardMove`, which reads the payload recorded at `dragstart` — the one moment the drag's own MIME type is certainly present.

- **The webview's navigation policy is native, not `beforeunload` (GH #138).** Cancelling `beforeunload` only *asks* the UA to prompt and the UA may decline, so it is not a veto and nothing in the frontend may be written as though it were. `src-tauri/src/navigation.rs` is a Tauri plugin whose `on_navigation` hook returns false — `WKNavigationActionPolicy::Cancel`, the load does not happen. It refuses every scheme that is not a page (`file:`, what a dropped image resolves to, plus `data:`, `blob:`, `javascript:`, `ftp:`, `about:`) and allows the app's own page, Tauri's own schemes, OS link handoff and `http(s)`.
  **The hook cannot tell a main frame from an iframe**, and that is a platform limit, not a choice: wry reads `action.request().URL()` and calls `function(url.to_string())` without touching `action.targetFrame` (`wry-0.55.0/src/wkwebview/navigation.rs:76`), and neither Tauri signature carries a frame (`tauri-2.11.0/src/plugin.rs:458`, `.../webview/webview_window.rs:266`). `BrowserPane`'s Generic mode frames arbitrary remote URLs and follows their links, so refusing remote pages would blank it. The top-level half of that case is held where the frame *is* known — in the page. Content here can reach the main frame three ways and `installNavigationGuard` refuses all three when they would leave the app's page: an anchor, a form (its own `action`/`target` or the submitting button's `formaction`/`formtarget`), and `window.open(url, "_self")`, whose first argument is stringified so a `URL` object counts too. A framed page cannot reach the main frame at all: the panes' iframes carry a `sandbox` without `allow-top-navigation`. `location` assignment is unforgeable and nothing in Ply assigns to it. **The condition for revisiting it:** Tauri exposing the target frame to `on_navigation`. Then narrow the main frame to the app's own document and keep the `http(s)` allowance for subframes only. Until then there is nothing to branch on — the response-policy hook is no help either (wry reads only `canShowMIMEType`, never `WKNavigationResponse.isForMainFrame`). The owner accepted this pushback.

- **Plyloft never runs `claude -p` / `--print` (Hard rule 1: Anthropic announced billing it outside the member's plan).** A Claude oneshot agent run (swarm roles included) and a Verify slash check are Claude's interactive TUI in a PTY, named with `--session-id` and collected through the session's transcript (`claude_session`, `PtyRegistry::begin_collect` + `CollectRun::wait`): an unattended writer session whose permission mode follows the member's own `defaultMode` (`claude_session::writer_mode`, 1.175.0: read in Claude's precedence, and only the member's own files — managed, user, the project's `settings.local.json` when it is plainly theirs: a real file under that exact name that no tracked path is — can choose bypass; the repository's `settings.json`, a tracked local file and every settings file in a card's copy may ask for accept edits, and a bypass they ask for is accept edits; in a copy the project's own local file comes before the copy's files; bypass stays bypass unless a layer disables it, `acceptEdits` becomes `dontAsk` with the edit tools allowed, anything else `dontAsk`), with `AskUserQuestion` disallowed and, for a swarm role, `Write` allowed for its artifact. The run ends with its turn; a blocking screen, the startup net (no transcript within 90 s and a still screen), a permission question mid-session (a tool call left without a result, the dialog drawn last) or the 4-hour net stops it, and Kill or Cmd-Q ends its process group. The oneshot run's stream parser reads the transcript's lines for its live log, model and usage; Claude reports no cost. `pty::refuse_print_mode` refuses a print-mode spawn and a guard test reads every source for one. REPL mode is unchanged.

- **Card-driven Kanban runs use card content as the prompt (v0.7.4 + v0.8.0 D2).** The agent's stored `promptTemplate` is bypassed for card-driven runs — `kanbanStore.moveCard` builds `[card.title, card.notes, card.knowledge].filter(present).join("\n\n")`. If you change the kanban → run path, preserve this.

- **Backend snapshot of file state is captured pre-spawn for oneshot runs (v0.9.0 F1).** `SnapshotsStore::capture_before` walks the cwd before `pty_spawn`. The exit listener calls `compute_changes` to write `changes.json`. Failure is best-effort — logs and continues. Don't make the snapshot path block the run.

- **`coordinator-feature` is the only builtin Swarm template that runs in coordinator mode (v1.5.1).** Defined in `src-tauri/src/swarm_templates.rs::builtin_templates()`. Unlike the sequential builtins (`feature`, `refactor`, `ux-audit`, `bugfix`), it declares a Coordinator that picks each tick which roles to dispatch in parallel from a pool of `scout`, `architect`, `builder`, `reviewer` (those `RoleStep`s function as the role pool, not an ordered chain). Invariant: the builtin definition must keep `coordinator: true` AND a non-empty `steps` pool — without both, coordinator mode either won't engage or has no roles to dispatch. Asserted by `builtin_coordinator_feature_has_coordinator_flag_and_role_pool` in the same file's tests; if you change the template, update that test in lockstep.

- **Card swarms run in parallel up to a configurable cap (v1.30.0).** `SwarmRegistry::validate_slot` admits card-kind swarms up to `Settings::card_swarm_cap()` (default 3, held as an `AtomicUsize` on the registry, seeded at startup + on `settings_set`); brainstorm/adhoc swarms stay one-at-a-time (shared cwd). Over-cap cards queue in the In Progress column — the queue is *derived*, not persisted: `kanban::card_is_queue_eligible` (In Progress + has `swarm_template_id` + `linked_swarm_id` null + `last_run_status != Failed` + not archived). `kanban::pump_card_queue` auto-starts queued cards as slots free; it's serialized by a process-wide mutex and hooked into `on_swarm_run_done`, `swarm_abort`, `settings_set` (cap raise), and opt-in startup. If you change the swarm-start path or the card lifecycle fields, keep the queue predicate honest. See `docs/STATUS.md` v1.30.0.

- **A PTY session is ended whole, never by one hangup (1.169.0, Hard rule 4).** On unix a tile, a Builder or an agent run is its own session (portable-pty calls `setsid`; a card chat's Claude ends through `ClaudeSessions::end` instead, the same hangup → kill of its group); `pty.rs::end_sessions` signals its leader's group and every process whose session it is (a shell's `cmd &` jobs run in groups of their own; macOS reads the process table): SIGHUP, then SIGTERM, then SIGKILL. The quit (`PtyRegistry::kill_all`) ends every live session at once within `QUIT_GRACE` (2 s, as a collected session's `COLLECT_KILL_GRACE`) and waits for it; a tile's close (`kill_with`) ends its session within `CLOSE_GRACE` (5 s) on a thread of its own and keeps it in `ending` until done, so a quit right after waits for it too. A session whose child was reaped (`PtySession.reaped`, set by every exit thread and a collected run's wait) is signalled nothing — its pid may belong to another process — and Plyloft's own group never; one reaped while being ended is signalled from then only through the members the process table still lists in it (a nohup'd or disowned job: it ends with the tile, as on Windows with the Job Object). Not covered, by design: what left the session itself (`setsid`: tmux, screen, a CLI's own background daemon). Windows ends the tile's Job Object instead (`TreeKiller`).
- **Setup's guided terminal runs only what Rust's allowlist builds (OB-3).** `setup_run(actionId, args?)` maps an id to an argv in `setup_actions.rs` (commands from `doctor::install_cmd_on` / `codex_update_cmd` / `gh_update_cmd`); the frontend never sends a command, and the one argument (`hostname`) must equal `github.com`. The PTY is `PtyRegistry::spawn_setup` with `ExecutionKind::Setup` — typed but **never recorded** in `coordination/state.json` (an older Ply would refuse the whole file over an unknown kind) — the cached PATH plus the probe's proxy variables, and the user's own `CODEX_HOME` (never a tile overlay). One run at a time: a second request is **refused** with words, not queued, and the slot is held until the watcher decides (the CLT dialog outlives `xcode-select --install`). Stop kills the process group (SIGTERM, SIGKILL after 2 s) or, on Windows, the tile Job Object's console processes; `ExitRequested` calls `setup_run::exit_cleanup` (SIGKILL, no new run) before `PtyRegistry::kill_all`. Success is observed (tool resolves + `--version` after a re-probe, credential appears, `xcode-select -p`), never the exit code alone; the frontend's `setupRunStore` listens before `setup_run` is invoked, so output printed before the answer (gh's one-time code) is not lost.

- **A card's Try session is a shell tile with a marker, and it never blocks a removal (Try it TI-2).** `pty_spawn(…, tryTarget)` → `PtyRegistry::spawn_tile` with a `try_session::TryTarget`: still `ExecutionKind::ShellTile` in the coordination record (a new kind would make an older Plyloft refuse `coordination/state.json`), still `session_env` (cached PATH, port block) plus `PORT=<port base>` in a card copy and `BROWSER=none`. The marker lives in the registry's memory only. It is **not** in `shell_tiles_in`, so `card_worktree_busy` ignores it; instead `try_session::stop_card_try_sessions` runs before every removal of a card's copy (local land, the PR ship's post-release prune, the ship backfill, archive, delete, a set-aside build, Put back's set-aside build). A removal stops only the card's Try sessions running **in a card copy** (`removal_selects`), never one in the project folder after Ship; the member's own stop (`stop_all_card_try_sessions`) takes all. The net is in the move itself: `move_to_trash_hooked` (behind `move_to_trash` and `move_to_trash_prepared`) stops any Try session inside the folder before the rename, and `prune_worktree_at` / `prune_one_at_tip` stop before stripping caches (on Windows a running server holds files there). A stop emits `card://try-stopped` with its reason (a ship's words: `STOPPED_FOR_SHIP_WORDS`). Killing one ends its command's process group on unix (the terminal's foreground job: SIGTERM, SIGKILL after 1.5 s; waited for before a removal and at quit), and on Windows the tile's Job Object (`TreeKiller`), which reaches `node` under `npm.cmd`. A new removal path calls the stop, or relies on ending in `move_to_trash_hooked`.
  - **Limits, accepted (no cwd sweep):** on the Mac a process that left the job — `setsid`, a daemon that double-forks, `nohup … &` into another group — is not reached; on Windows a GUI window the command opened is spared, as for every tile (the job ends console processes only). If such a process holds the copy, the removal goes on as today: a move that fails keeps the copy, and the paths that report a kept copy (Ship's put-away, Sync's merged prune, delete) say so and why; archive logs it; nothing is forced.
  - **PowerShell `.cmd` shims:** a Try session types `npm.cmd` (`pnpm`, `yarn`, `npx`, `bun`) only when `try_cmd_shims_available` finds that `.cmd` on the cached PATH; otherwise the command is typed as the member wrote it.
